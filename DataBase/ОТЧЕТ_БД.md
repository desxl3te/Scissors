Отчёт о тестировании базы данных «scissors_bar»
1. Объект тестирования
Объектом тестирования является схема базы данных scissors_bar. В её состав входят таблицы: users, tables, reservations, menu_items, categories, orders. Также тестировалась хранимая процедура BookTable. Тесты написаны на языке SQL (ручные сценарии), а также на Python с использованием фреймворка pytest.

2. Объём тестирования
В ходе тестирования были проверены 5 основных таблиц на предмет структуры, связей и ограничений. Написано и выполнено 18 автоматических тест-функций, распределённых по файлам Safety.py, autho_test.py, BookTable.py и test_queries.py. Дополнительно проведено 12 ручных SQL-сценариев, включая проверки CRUD-операций, репликации, выполнения планов запросов через EXPLAIN и проверку ключей. Всего тестирование охватило следующие аспекты: схема данных, CRUD-операции, уникальность полей, внешние ключи, CHECK-ограничения, значения по умолчанию, транзакции, производительность (через EXPLAIN) и безопасность (устойчивость к SQL-инъекциям).

3. Результаты автоматических тестов
3.1 Файл autho_test.py (целостность и ограничения)
Все тесты из данного файла были пройдены успешно. Подключение к базе данных установлено, все требуемые таблицы присутствуют в схеме. Ограничение уникальности для поля email срабатывает корректно, не позволяя вставить двух пользователей с одинаковым адресом. Проверка CHECK-ограничения на поле price в таблице menu_items также отработала правильно, отклонив вставку записи с отрицательной ценой. Тест внешнего ключа для таблицы orders был пропущен, поскольку сама таблица orders в текущей версии базы данных отсутствует. Значение по умолчанию для поля role в таблице users установлено как customer, и это работает верно. Транзакции поддерживаются корректно: при выполнении ROLLBACK вставленные данные не сохраняются в базе.

3.2 Файл Safety.py (SQL-инъекции)
Все проверки на SQL-инъекции пройдены. Параметризованный запрос не пропустил атаку обхода авторизации со строкой ' OR '1'='1. UNION-атака, пытавшаяся извлечь данные из других таблиц, не сработала. Деструктивная попытка удалить таблицу users через инъекцию '; DROP TABLE users; -- также не возымела эффекта — таблица осталась нетронутой, все данные сохранены. Вредоносная строка, переданная в хранимую процедуру, была сохранена как обычный текст, а не выполнена как SQL-код.

3.3 Файл BookTable.py (хранимая процедура)
Тестирование процедуры BookTable показало, что при корректных входных данных бронь успешно создаётся со статусом confirmed. При попытке забронировать столик для несуществующего пользователя процедура возвращает ошибку 1644 с текстом «пользователь не найден». Аналогично, если указан несуществующий столик, возникает ошибка 1644 с текстом «столик не найден». При попытке забронировать уже занятый на это время столик процедура выдаёт ошибку 1644 с текстом «уже забронирован». Также была подтверждена работа CHECK-ограничения на поле guests_count — отрицательное количество гостей не было пропущено.

3.4 Файл test_queries.py (запросы к меню и столикам)
Все тесты из этого файла выполнены успешно. При запросе обычного меню секретные блюда в выдачу не попали. При запросе секретного меню, наоборот, обычные блюда отсутствовали. Оба тестовых столика (активный и неактивный) были найдены при запросе всех столиков. При проверке свободных столиков на конкретное время занятый столик был корректно исключён из результатов. Все брони, созданные для тестового пользователя с идентификатором 1, действительно принадлежали этому пользователю. Запрос по столику 3 и времени 20:00 вернул ровно одну бронь, как и ожидалось.

4. Результаты ручного тестирования (SQL-скрипты)
4.1 CRUD-операции
В ходе выполнения скриптов create_test.sql, read_test.sql, update_test.sql и delete_test.sql были успешно протестированы вставка, чтение, обновление и удаление записи с email test@example.com. Данные изменяются корректно на уровне прямых SQL-запросов без использования ORM.

4.2 Структура и ключи
Скрипты structure_test.sql и table_test.sql подтвердили, что таблица users содержит все необходимые поля, а список таблиц в схеме scissors_bar получен без ошибок. Скрипт keys_test.sql подготовлен, но фактическая проверка внешних ключей в данном отчёте не проводилась из-за отсутствия вывода команды SHOW CREATE TABLE.

4.3 Репликация
Скрипт replication_test.sql описывает правильную логику проверки репликации: вставка на основном сервере (мастере) и последующее чтение на реплике (слейве). Однако фактическое тестирование репликации не выполнялось, поскольку для этого требуется настроенный кластер Master-Slave.

4.4 Аналитика и производительность
Анализ планов выполнения запросов через EXPLAIN (скрипты analytics_explain_test.sql и explain_index_test.sql) показал, что на поле users.email отсутствует индекс. Это может привести к замедлению запросов при росте объёма данных. Все аналитические запросы (группировка, сортировка, вычисление среднего, LIMIT) были проанализированы, их планы выполнения признаны приемлемыми для тестового объёма данных.

4.5 Тестовые данные
Скрипт test_data.sql успешно добавил тестового пользователя test_user и 11 тестовых броней (одна из которых имеет статус cancelled). Все данные вставлены корректно.

5. Найденные недостатки и ограничения
В ходе тестирования выявлены следующие недостатки:

Отсутствует индекс на поле users.email. При выполнении запросов с условием WHERE email = … производительность будет снижаться по мере роста таблицы. Серьёзность — средняя. Статус — открыт.

Таблица orders не создана в текущей версии схемы. Если она требуется по бизнес-логике, это является пропуском. Серьёзность — низкая (при условии, что таблица не нужна). Статус — открыт.

Репликация Master-Slave не протестирована в автоматическом режиме. Для полноценной проверки требуется развёрнутый тестовый стенд. Серьёзность — средняя. Статус — требуется стенд.

В хранимой процедуре BookTable отсутствует явная валидация отрицательного значения guests_count до попытки вставки. В текущей версии ошибка возникает на уровне CHECK-ограничения, что допустимо, но для улучшения диагностики рекомендуется добавить раннюю проверку. Серьёзность — низкая. Статус — рекомендация.

6. Рекомендации
По итогам тестирования рекомендуется:

Добавить индекс на поле users.email для ускорения поисковых запросов.

Создать таблицу orders, если она предусмотрена архитектурой приложения и необходима для бизнес-логики.

Развернуть тестовый Master-Slave кластер и провести автоматизированную проверку репликации.

Дополнить хранимую процедуру BookTable проверкой IF p_guests_count <= 0 THEN SIGNAL ... для более понятной обработки ошибок.

Внедрить запуск всех pytest-тестов в CI-процесс перед каждым обновлением схемы базы данных.

7. Вывод
Основной функционал базы данных, включая CRUD-операции, ограничения целостности, работу хранимой процедуры и механизмы защиты от SQL-инъекций, работает корректно. Автоматические тесты покрывают критические сценарии: устойчивость к инъекциям, транзакции, внешние ключи и CHECK-ограничения. Производительность на имеющемся тестовом объёме данных оценивается как удовлетворительная. Проект может быть передан на дальнейшее тестирование после исправления замечаний, связанных с индексацией и репликацией.
